## 0. 一句话说清这个库是什么

**知危鉴（ZhiWeiJian）** 是一个面向应急管理的「**风险预警 + 案例复盘**」智能平台。它把"看灾害新闻/查案例"升级为一条闭环：

> 在线数据获取 → 清洗与标准化 → 多维风险识别 → 分级预警 → 态势可视化 → 案例复盘 → 处置建议

代码库里其实并存**两套实现**（下文第 3 节讲清楚为什么），它们共享同一个品牌与同一套方法论，只是面向不同使用场景：一套用于**在线演示/参赛托管**，一套用于**工程化全栈部署**。

## 1. 命名统一（先把"名字乱"这件事解决）

### 1.1 最终结论：只保留一个品牌名

| 项目 | 采用名称 | 说明 |
|---|---|---|
| **正式品牌名** | **知危鉴（ZhiWeiJian）** | 全库唯一对外品牌，代码/UI/文档统一用这个 |

- **降低认知成本**：评审/用户第一次打开，看到"知危鉴 / CaseRescue / 知灾析策"三个名字会困惑"这到底是几个产品"。
- **避免自我稀释**：一个作品两个品牌，等于把注意力劈成两半，评审记不住。
- **便于检索与传播**：单一名字更容易被记住、被搜到、被引用。

### 1.3 统一规则（写代码/写文档时照这个来）

- 页面标题、侧边栏、Logo、`<title>`、API 文档标题：一律写 **知危鉴**。
- "案例复盘"作为**功能名**出现（如"案例复盘模块"），不再写"CaseRescue 知灾析策 子品牌"。
- 英文标识别统一为 `ZhiWeiJian`（仓库名 `zhiweijian` 保持不变，避免改仓库地址导致部署中断）。

> 备注：仓库名/部署子域名仍是 `zhiweijian`，这是"知危鉴"的拼音，属正常，不必改。改名只针对**展示层文案**，不动仓库名与部署配置。

## 2. 产品定位、目标用户与痛点

### 2.1 定位
- 面向应急管理场景的**"知危"（风险识别/预警）+ "鉴验"（案例复盘/经验沉淀）**平台。
- 从原来的"Coze 关键词问答 → 知识卡片"升级为"数据 + 风险 + 预警 + 案例"的**可上线 Web 应用**。

### 2.2 目标用户
| 用户 | 关心什么 |
|---|---|
| 应急管理部门/指挥人员 | 某区域当前风险等级、是否需要发预警、怎么处置 |
| 监测/值守操作员 | 实时指标跳动、越限报警 |
| 科研/分析师/学生 | 真实案例的结构化复盘、可迁移经验 |
| 公众/企业 | 简明预警与应急指南 |

### 2.3 解决的痛点
1. 灾害信息**分散**在各地官网、报告里，人工搜集整理成本高。
2. 监测指标**看不出风险**：有一堆数字，但"现在到底危险不危险"没人替你判断。
3. 案例复盘**没有统一模板**：每个人整理的格式五花八门，不利于对比学习。
4. 预警与处置**脱节**：知道有风险，但不知道该谁做、做什么。

## 3. 整体架构：为什么有两套栈

这是本库最需要说清楚的一点，也是"看起来乱"的根源。

### 3.1 两套栈总览

| | **Stack B：在线演示栈（Streamlit）** | **Stack A：工程化全栈（FastAPI + 静态前端）** |
|---|---|---|
| 位置 | `streamlit/zhiweijian/` | `backend/` + `frontend/` + `web/` |
| 用途 | **参赛托管 / 在线体验**（已部署到 Streamlit Cloud） | **可上线的完整前后端**（Docker 一键起） |
| 数据 | **真实在线 API**（USGS 地震 / Open-Meteo 天气 / NHC 台风） | **内置样例数据**（可替换为数据库/流式） |
| 亮点 | 真实数据、地图态势、MPA 复盘方法论、SCI 学术视觉 | 风险引擎、预警规则、RAG 检索、REST API、SSE 实时流 |
| 一句话 | "能马上点开看效果的作品" | "能真正部署给部门用的系统骨架" |

### 3.2 两栈是什么关系（设计取舍）
- **同一品牌、同一方法论、两套实现**：Stack B 偏"展示与体验"，Stack A 偏"工程与扩展"。
- 之所以不合并：Streamlit 上手快、能直接托管、适合参赛演示；但它不适合做真正的多用户后端（鉴权、并发、数据库）。FastAPI 那套是为"将来给真实部门落地"准备的骨架。
- **由此带来的代价**：两套 UI 的文案/命名/数据不一致，容易让人觉得"乱"。本文档统一口径：**对外以知危鉴为唯一品牌；演示看 Stack B，工程看 Stack A。**

### 3.3 分层图（两栈共用的逻辑分层）

```
┌─────────────────────────────────────────────┐
│ 表现层  Streamlit 页面 / 静态 HTML+ECharts    │

│ 服务层  风险识别引擎 / 预警规则 / 案例RAG     │
├─────────────────────────────────────────────┤
│ 数据层  在线API(USGS/Open-Meteo/NHC) / 样例数据│
└─────────────────────────────────────────────┘
```

## 4. 端到端业务流程（每一步"为什么做、做什么、落在哪"）

| 步骤 | 目的 | 输入 → 输出 | 代码落点 |
|---|---|---|---|
| ① 在线数据获取 | 拿到"活的"原始数据 | 无 → 地震/天气/台风原始 JSON | `data_online.fetch_usgs / fetch_weather / fetch_typhoon_tracks_online` |
| ② 清洗与标准化 | 去重、补字段、统一格式，让脏数据变可计算 | 原始 → 统一 Case 结构 | `data_online.clean_unify` |
| ③ 整合 | 多源合成一份态势数据集 | 多源 → `build_dataset()` 字典 | `data_online.build_dataset / integrate_dataset` |
| ④ 风险识别 | 把"数字"变成"危险程度" | 多维信号 → 风险分 + 等级 + 建议 | `engine.risk_identify`（Stack A） |
| ⑤ 预警匹配 | 指标越限就报警 | 指标 × 规则 → 预警事件 | `engine.match_alerts`（Stack A） |
| ⑥ 态势可视化 | 让人一眼看懂"哪里危险" | 数据 → 地图/图表/仪表盘 | `app.tab_map / tab_search_viz / tab_weather`（Stack B） |
| ⑦ 案例复盘 | 从历史案例提炼可迁移经验 | 关键词 → 结构化知识卡片 | `engine.case_query / rag.CaseRAG` + `data_online.enrich_case` |
| ⑧ 处置建议 | 把"复盘"转成"行动" | 风险等级 → 处置/防范建议 | `engine._suggestion` + `data_online.EMERGENCY_PLANS` |

## 5. 模块逐项说明（全部功能，一项不落）

### 5.1 Stack B · Streamlit 在线应用（`streamlit/zhiweijian/app.py`）

页面框架：`set_page_config`（宽屏、⚠️ 图标）→ 侧边栏（品牌 + 自动刷新 + 刷新间隔 + **深色模式开关**）→ 底部 `radio` 切换 4 个模块。

#### 5.1.1 模块一：在线态势地图 `tab_map()`
- **作用**：一张地图统一承载"实时状态 + 历史数据"。
- **图层**：
  - 🌏 实时地震（USGS）：`CircleMarker`，半径 ∝ 震级，红色（危害语义色）。
  - 🌀 台风历史轨迹：`PolyLine` 虚线 + 起/终点标记（NHC 在线，不可达时用内置 IBTrACS 回退）。
  - ⚠️ 隐患点：从 M≥6 地震提取高风险点，菱形标记（高危红 / 低危琥珀）。
- **图例**：左下角白色卡片，标注三类要素（学术图规范）。
- **底图**：浅色默认 `CartoDB Positron`（细线学术底）；深色模式切 `CartoDB Dark Matter`。
- **交互**：`LayerControl` 图层开关 + `fit_bounds` 自动缩放。
- **设计取舍**：用 folium（Leaflet）而非 ECharts 地图，因为 folium 对"轨迹线 + 点 + 弹窗"最省事；底图选 CartoDB 是因为它自带细边界线、无花哨 POI，最像"学术制图"。

#### 5.1.2 模块二：在线搜索 · 数据整合 · 可视化 `tab_search_viz()`
- **作用**：把"搜索→清洗→整合→分析"一条龙做完，是"数据萃取"的落点所在的模块。
- **筛选**：关键词（全字段模糊匹配）、区域（中国大陆/沿海/日本/东南亚 经纬度框）、最小震级滑块。
- **处理链**：`clean_unify`（去重+标准化）→ `enrich_case`（补复盘三层信息）。
- **KPI 仪表盘**：事件总数 / 最大震级 / ≥M6 数 / ≥M5 数。
- **MPA 方法论四个视图**（这是本模块的"学术含量"）：
  - 🎬 **冲突叙事时间轴**：按"平稳→突发冲突→多次应对→最终蜕变"归组排序，而非纯时间平铺。
  - 🔍 **三层视角**：政策层 / 地方层 / 现场层 三维拆解。
  - 📑 **证据来源分布**：六类证据（官方报告/深度访谈/现场观察/档案/新闻/影像）交叉印证 + 强度分级。
  - ⚖️ **横向对照验证**：同类灾害不同处置效果的评分矩阵（堆叠柱状图）。
- **三标签页**：📈 图表（震级分布直方图 + 震中空间散点）/ 📋 表格（原始数据）/ 📖 案例复盘卡（过程线→动因→可迁移经验 + 证据强度 + 叙事阶段）。
- **设计取舍**：在线数据（USGS）本身没有"复盘深度"，所以用 `enrich_case` 按灾害类型套标准模板，保证每条卡片都有结构，而不是空壳。

#### 5.1.3 模块三：应急方案模块 `tab_plan()`
- **作用**：把"预案"变成可查、可执行的结构化流程。
- **依据**：**GB/T 29639-2020**《生产经营单位生产安全事故应急预案编制导则》。
- **5 个环节**（`EMERGENCY_PLANS`）：预警与报告 / 响应启动 / 疏散与警戒 / 抢险与医疗 / 后期处置。
- **每环节字段**：触发条件 / 责任人 / 响应级别 / 处置步骤 / 流程链（含责任人）。
- **可视化**：流程链用 Altair 色块图，区分"报告/判级"（琥珀）与其他环节（蓝）。
- **设计取舍**：内置规范数据（无本地文件、无需联网），保证离线也能演示"专业度"。

#### 5.1.4 模块四：实时天气仪表盘 `tab_weather()`
- **作用**：在线取某城市实时天气，服务"气象类风险"判断。
- **链路**：城市名 → `geocode_online`（Open-Meteo 地理编码）→ `fetch_weather`（当前温度/风速/降水/湿度）→ 指标卡 + 柱状图。
- **设计取舍**：走 Open-Meteo 免费 API，无需密钥；失败有兜底坐标与提示，不阻断页面。

#### 5.1.5 数据层 `data_online.py`（每个函数）
| 函数 | 作用 |
|---|---|
| `_http_json / _http_text` | 统一 HTTP 抓取（带 UA、超时、异常吞掉返回 None） |
| `fetch_usgs(min_mag)` | 拉 USGS 近一周地震 GeoJSON → 标准化 Case（缓存 600s） |
| `geocode_online(city)` | 城市名 → 经纬度（Open-Meteo 地理编码） |
| `fetch_weather(lat,lon,city)` | 当前天气（温度/风速/风向/降水/湿度） |
| `clean_unify(raw)` | 去重 + 补字段 + 经纬度取整 + 日期规范 |
| `integrate_dataset(eq,ty)` | 地震+台风合并为统一态势集 |
| `fetch_typhoon_tracks_online()` | 解析 NHC ATCF 文本 → 取最近 3 条轨迹 |
| `fetch_risk_spots(eq)` | M≥6 地震取前 5 → 隐患点（等级 3/4） |
| `build_dataset(min_mag)` | 组装最终数据集（USGS + NHC，失败回退内置 IBTrACS） |
| `enrich_case(c)` | 补 过程线/动因/可迁移经验/证据类型强度/叙事阶段/三层视角 |
| `narrative_timeline / three_layer_view / comparison_matrix / evidence_summary` | MPA 复盘四件套的装配函数 |
| `EMERGENCY_PLANS` | GB/T 29639-2020 五环节预案数据 |
| `EVIDENCE_TYPES/STRENGTH/NARRATIVE_PHASES/THREE_LAYERS` | 复盘方法论常量 |

#### 5.1.6 全局视觉（SCI 学术美感 + 明暗双模）
- **浅色（默认）**：GV 米白纸张底 `#F7F8FA` + a16z 衬线大标题（Noto Serif SC）+ 克制金棕品牌色 `#A6761D`；数据读数等宽（JetBrains Mono）。
- **深色**：a16z 深炭黑底 `#0B1430` + 金色强调 `#C9972E`。
- **实现**：两段 `<style>`（`_SCI_CSS` + `_DARK_CSS`）注入，侧边栏开关控制。

### 5.2 Stack A · FastAPI 后端（`backend/app/`）

#### 5.2.1 契约层 `models/schemas.py`
| 模型 | 作用 |
|---|---|
| `AlertLevel` | 四级预警枚举：蓝(1)/黄(2)/橙(3)/红(4)，含中文名与十六进制配色 |
| `RiskDimension` | 单个风险维度（key/label/value/weight） |
| `RiskAssessment` | 风险识别结果（灾种/区域/分数/等级/维度明细/建议） |
| `AlertRule` | 预警规则（指标/阈值/比较符/触发级别/开关） |
| `AlertEvent` | 触发的预警事件 |
| `CaseCard` | 案例知识卡片（概况/风险因素/措施/教训/标签/来源） |
| `RegionMetric` | 区域监测指标（值/单位/趋势/状态） |
| `TrendPoint` | 时序点 |

#### 5.2.2 引擎 `services/engine.py`
- `risk_identify(hazard, region, signals, drivers)`：按灾害类型取权重（`_WEIGHTS`），多维度加权求和 → 0-100 分 → 按阈值（80/60/40）定级 → 附处置建议。
- `match_alerts(metrics, rules)`：指标 × 规则逐条匹配（支持 `>= > <= < between`）→ 产出 `AlertEvent`。
- `case_query(cases, keyword, top_k)`：关键词在标题/标签/概况/措施/教训加权打分检索。
- **设计取舍**：纯函数 + 内存数据，无外部依赖，`python run.py` 即可跑通；接真实数据库只需替换 `data/`。

#### 5.2.3 RAG `services/rag.py`
- `CaseRAG`：TF-IDF 向量化 + 余弦相似度检索，支持多词/近义（比原"子串匹配"召回更稳）。
- `report()`：检索结果 + 风险评估 → 结构化复盘报告（模板装配，字段稳定，可平滑替换为大模型生成）。
- **设计取舍**：用 TF-IDF 而非大模型/向量库，是为了**零密钥、纯 CPU、可离线**，先保证能跑；将来换 LLM 时接口不变。

#### 5.2.4 实时流 `services/live.py`
- `live_stream()`：SSE 推送，每 ~2s 一帧"指标随机游走 + 触发预警"，模拟实时监测跳动。
- **设计取舍**：真实数据源未接入前，用随机游走演示"实时感"，接口形态（SSE）与真实场景一致。

#### 5.2.5 路由 `routers/api.py`（全部端点）
| 方法 | 路径 | 作用 |
|---|---|---|
| GET | `/api/health` | 健康检查 |
| GET | `/api/cases?keyword&top_k` | 案例关键词检索（知识卡片） |
| GET | `/api/cases/rag?keyword&top_k` | TF-IDF 相似度检索（带相似度分） |
| GET | `/api/cases/report?keyword&hazard&region` | 自动装配复盘/分析报告 |
| GET | `/api/monitor/metrics` | 监测指标 |

## 6. 关键设计考量与取舍（为什么这么设计）

| 决策点 | 选择 | 理由 | 代价 / 后续 |
|---|---|---|---|
| 纯在线 vs 本地缓存 | **纯在线**（Stack B 不落盘） | 契合"在线作品托管"，数据永远是最新的 | 依赖外部 API 可用性；已用缓存(600s)+回退缓解 |
| 样例数据 vs 真数据库 | **样例数据**（Stack A） | 演示/评审无需部署数据库即可跑 | 非真实规模；已按"可替换"设计 |
| TF-IDF vs 大模型 | **TF-IDF**（RAG） | 零密钥、纯 CPU、可离线、可复现 | 语义能力弱于大模型；接口预留替换 |
| 模板报告 vs LLM 生成 | **模板装配** | 字段稳定、可控、无幻觉 | 语言不够自然；可接 LLM |
| 四级预警 | **蓝黄橙红** | 对齐中国突发事件预警惯例 | — |
| 应急预案 | **GB/T 29639-2020** | 有国标背书，专业可信 | 需按行业细化 |
| 两套栈并存 | **Streamlit + FastAPI** | 一个快演示、一个能落地 | 文案/数据需统一口径（本文档职责） |
| MPA 复盘方法论 | **证据分级/冲突叙事/三层视角** | 让"复盘"有学术框架，不是流水账 | 需持续补充真实案例 |

## 7. 关于"萃取"——回应你的重复疑虑

### 7.1 现状：本库里的"萃取"到底是什么
目前"萃取"二字**只出现在两处**，指的是**同一件事**——"把在线数据取下来、清洗成图表/CSV"：
- `streamlit/zhiweijian/README.md`：`在线搜索与数据萃取`、`数据萃取展示`。
- `web/index.html`：`数据萃取到图表`、`萃取 CSV`、`天气（在线搜索 + 萃取）`。

它**不是独立功能/独立模块**，本质就是第 4 节流程里的 ①获取 + ②清洗 + ⑥可视化，落在 `tab_search_viz()` 里。

### 7.2 和"之前那个项目"是否重复
- 如果你之前的项目（也做过取数/萃取）做的是**别的领域**，那本库的"萃取"是**灾害应急领域**的取数，属**同手段、不同场景**，不算功能重复。
- 但如果两者都叫"萃取"、且都在做"在线取数→图表"，那**概念上会撞车**，让评审觉得"这不就是又做了一遍取数吗"。

### 7.3 建议（二选一，需你拍板）
- **方案 A（推荐）：保留能力、改称呼**。把 UI/文档里的"数据萃取"统一改称「**在线数据整合**」或「**态势数据获取**」，明确它服务于"风险态势"，而不是一个"通用取数工具"。这样既保留功能，又不与旧项目概念冲突。
- **方案 B：弱化展示**。如果旧项目已充分展示"萃取"能力，本库就把相关入口收进"在线搜索·可视化"里，不再单列"萃取"字样。

> 结论：**能力要留（它是态势地图/搜索的数据来源），但"萃取"这个词要换掉**，避免重复感。等你确认 A 还是 B，我再统一改文案。
